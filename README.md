# ELEZON — B2B equipment catalog

A modern, bilingual (RU/EN) B2B catalog site for **Elezon**, a Russian engineering supplier of
building-automation, instrumentation (КИП), low-voltage and KNX equipment. There is **no direct
checkout** — every action routes to a price request (Запрос цены) or stock check, matching the B2B
model. Implemented in **Vite + React + TypeScript** from a Claude Design handoff (Concept A).

This repo contains two apps built from one design system:

- **Storefront** (`index.html` → `src/main.tsx`) — public catalog
- **Admin panel** (`admin.html` → `src/admin/main.tsx`) — Supabase-backed management console behind auth

Data lives in **Supabase** (Postgres + Auth + RLS + Realtime). With no env configured the
apps fall back to the bundled demo catalog (`ELEZON_DATA`), so the UI still runs offline.

## Stack

- Vite 5 (multi-page build), React 18, TypeScript (strict)
- React Router 6 (real URLs for SEO)
- No CSS framework — hand-authored design tokens (`src/styles/tokens.css`) using OKLCH colors;
  fonts Onest / Unbounded / JetBrains Mono

## Getting started

```bash
npm install
cp .env.example .env  # then fill in VITE_SUPABASE_URL + VITE_SUPABASE_ANON_KEY
npm run dev          # storefront at /, admin at /admin.html
npm run build        # typechecks (tsc -b) then builds both entries
npm run preview      # preview the production build
npm run typecheck
```

The anon key is **public-safe** — every table is protected by Row-Level Security (see below).
Without `.env`, the apps run on the bundled demo data and all writes are no-ops.

## Key behaviors

- **Bilingual:** RU is the source language; EN comes from one dictionary. The toggle (top-right) is
  persisted to `localStorage` and shared between storefront and admin.
- **Request list:** the B2B alternative to a cart. Add from product cards (`+`) or the product page,
  manage quantities on `/request`, submit one batched price request. Persisted to `localStorage`.
- **No checkout:** all CTAs lead to "Запрос цены / Request price" or stock/contact.

## Admin panel

Served at `/admin.html` (or `/admin` on Vercel). Behind a Supabase Auth login gate — only users
listed in the `admins` table can sign in. Light content area + dark graphite top bar, same tokens
and i18n. Sections: dashboard, products, categories, brands, requests (заявки), customers,
content, settings, subscriptions (подписки). All CRUD persists to Supabase; new storefront
requests and restock subscriptions stream in live via Realtime.

## Backend (Supabase)

Postgres schema, seed and policies live under `supabase/`:

| File | Purpose |
|------|---------|
| `migrations/0001_init.sql` | Tables + Row-Level Security + `is_admin()` / `admins` allow-list |
| `migrations/0002_webhooks.sql` | INSERT triggers → notify Edge Functions (pg_net) |
| `seed.sql` | Demo catalogue/content/settings/stats (generated by `scripts/gen-seed.ts`) |
| `functions/notify-order`, `functions/notify-lead` | Email notifications via Resend |

**RLS model:** `anon` can read the catalogue/content/settings/stats and **insert** orders +
stock_leads (insert-only, no select). All PII (customers, orders, stock_leads) is readable only by
an authenticated **admin**, defined as a row in `public.admins` and checked by the
`is_admin()` SECURITY DEFINER function. **Disable public sign-ups** in Auth → Providers so nobody
can self-register as an authenticated user.

### First-time setup

1. Create a Supabase project; copy the URL + anon key into `.env`.
2. Run `supabase/migrations/0001_init.sql` then `supabase/seed.sql` in the SQL Editor.
3. Create your admin user (Auth → Users → Add user), then add them to the allow-list:
   `insert into public.admins (user_id) values ('<that-user-uuid>');`
4. Auth → Providers → Email → turn **Allow new users** off.

## Email notifications (Resend)

New requests and restock subscriptions email the company. Flow:
`orders` / `stock_leads` INSERT → DB webhook (`0002_webhooks.sql`) → Edge Function → Resend.

```bash
# one-time: Supabase CLI
npm i -g supabase
supabase login
supabase link --project-ref qynfoajwaamqgofqdzso

# secrets (never committed — live only in Supabase)
supabase secrets set RESEND_API_KEY=re_xxx
supabase secrets set NOTIFY_EMAIL=info@elezon.ru
supabase secrets set NOTIFY_FROM="ELEZON <notify@elezon.ru>"
supabase secrets set WEBHOOK_SECRET=<random-long-string>

# deploy the functions (verify_jwt is off via config.toml)
supabase functions deploy notify-order
supabase functions deploy notify-lead
```

Then wire the webhook secret into the database and run the trigger migration:

```sql
-- SQL Editor — store the same WEBHOOK_SECRET in Vault, then run 0002_webhooks.sql
select vault.create_secret('<same-WEBHOOK_SECRET>', 'elezon_webhook_secret');
```

> **Resend test mode:** until a domain is verified, `NOTIFY_FROM` must be
> `onboarding@resend.dev` and `NOTIFY_EMAIL` must be the Resend account owner's email. To send
> from `notify@elezon.ru` to `info@elezon.ru`, verify `elezon.ru` in Resend → Domains (add the
> DNS records), then update the two secrets.

## Deploy (Vercel)

`vercel.json` sets the build, SPA rewrites (`/admin` → `admin.html`, deep links → `index.html`)
and security headers (HSTS, `X-Frame-Options: DENY`, CSP scoped to the Supabase origin, etc.).

1. Import the repo in Vercel.
2. Add env vars `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY` (Production).
3. Deploy. The storefront is at `/`, the admin at `/admin`.
4. If you add a custom domain, update the `connect-src`/origins in `vercel.json` CSP and the
   Supabase Auth redirect URLs accordingly.

### Production checklist

- [ ] `.env` **not** committed (`.gitignore` covers `.env*`)
- [ ] Public sign-ups disabled in Supabase Auth
- [ ] Admin user added to `public.admins`
- [ ] Edge Function secrets set; `WEBHOOK_SECRET` matches the Vault secret
- [ ] A real request sends an email to `NOTIFY_EMAIL`
- [ ] Security headers present (check with `curl -I`)
